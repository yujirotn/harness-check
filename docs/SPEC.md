# ハーネス点検 仕様書（v2.1）

2026-11-11 確定。採点の中身を変えるときは、先にこのファイルを直す。
v2.1 は、1周目のレビューで見つかった仕様の不備を直したもの。変更点は12章にまとめてある。

## 1. これは何か

AIエージェント（Claude Code、Codex など）を使っている人が、自分の「ハーネス」を自分で点検する道具。
ハーネスとは、AIの周りに置く設定・指示・道具の一式のこと。

使い方は1つ。利用者が自分のAIに「このリポジトリを読んで、手順どおりに私の環境を点検して」と頼む。
AIが手順書に従って事実を集め、点数つきのレポート（PDF）を出す。

- 主な利用者は、自分で走らせる個人。研修で使う場合も、同じ道具を各自が走らせる。
- 特定の会社やチームの事情は、この道具に持ち込まない。

## 2. 設計の原則

1. **道具に依らない点検項目と、道具ごとの読み取り部品を分ける。** 項目は `items.json` の1か所で定義する。道具ごとの事実の集め方は `readers/` に置く。最初の部品は Claude Code と Codex。
2. **測れないものは×にしない。** 「測定できず」として、点数の分母から外す。
3. **割合は採点しない。** 採点に使うのは、「ある／ない」と「直近30日に1回以上の記録がある／ない」の二値だけ。回数や行数は参考欄に生の数で載せる。
4. **1つの設定は1つの項目でしか数えない。**
5. **判定の出どころを必ず示す。** 項目ごとに「機械」「AIの判断」「本人の回答」のどれで決めたかをレポートに出す。
6. **「人が入らないほど良い」とはしない。** 任せ方の柱と安全の柱を別に立て、両方を見る。
7. **読むだけ。** 利用者のPCに書き込むのは、出力フォルダの中だけ。通信はしない。
8. **秘密と固有名を出さない。** キーの値は絶対に出力しない。フォルダ名・ファイルの本文・会話の本文は、レポートに出さない。**スキル・エージェント・コネクタの名前も、既定では出さない**（取引先名などが入っていることがあるため）。名前は、本人が `--show-names` を指定したときだけ出す。
9. **起動してよい外部プログラムは、Git と Chrome だけ。** それ以外は起動しない（5-7）。

## 3. 点数

- 柱は4本。柱ごとに「満たした数 ÷ 判定できた数」を出す。
- **点数は、4本の柱の達成率の平均を100点満点にして四捨五入したもの。** 判定できた項目が0の柱は、平均から外す。
- 点数の横に「23項目中○項目を判定」を必ず添える。
- 合計点のほかに「型」の名前を出す（6章）。レベルや順位は出さない。

## 4. 点検項目（23項目）

判定の種類: **機械**＝スクリプトが決める ／ **AI**＝AIが決まった質問に「はい・いいえ」で答える ／ **機械＋AI**＝機械で○にならなかったときだけAIが判定する。

「使用の記録」は、直近30日の会話の記録から数える。

### 土台（11項目）― 道具が揃い、使われているか

| ID | 項目 | 判定 | Claude Code での見方 | Codex での見方 |
|---|---|---|---|---|
| F1 | 作業フォルダに指示書がある | 機械 | 作業フォルダからGitのルートまでに `CLAUDE.md` か `.claude/CLAUDE.md` がある | 同じ範囲に `AGENTS.md` がある |
| F2 | 毎回読まれる指示ファイルが、どれも長すぎない | 機械 | 起動時に読まれるファイル（全体用と作業フォルダ用の `CLAUDE.md`、`CLAUDE.local.md`、`paths` 指定のない rules（作業フォルダの `.claude/rules/*.md` と、全体用の `~/.claude/rules/*.md` の両方。リンクになっている場合はリンク先を読む）、`@` で読み込まれるファイル）が、どれも200行未満 | 読まれる `AGENTS.md` の合計が32KiB未満 |
| F3 | 指示が具体的で、守れたか確かめられる | AI | 作業フォルダ用の指示書を読んで判定 | 同じ |
| F4 | 矛盾する指示がない | AI | 起動時に読まれる指示ファイル全体を読んで判定 | 同じ |
| F5 | 自分で用意したスキルがある | 機械 | `~/.claude/skills/` か作業フォルダの `.claude/skills/` に1本以上。プラグイン同梱は数えない | `~/.agents/skills/` か作業フォルダの `.agents/skills/` に1本以上 |
| F6 | 自分で用意したスキルが、直近30日に1回以上使われた | 機械 | 会話の記録に、F5のスキル名での呼び出しがある | 測定できず |
| F7 | スキルの説明文に「何をするか」と「いつ使うか」がある | AI | 使われた自作スキルを回数の多い順に最大5本。なければ更新の新しい順に最大5本。全部が満たせば○ | 同じ（更新の新しい順） |
| F8 | エージェントの定義がある | 機械 | `~/.claude/agents/` か作業フォルダの `.claude/agents/` に1つ以上 | `~/.codex/agents/` か作業フォルダの `.codex/agents/` に1つ以上 |
| F9 | 自分で定義したエージェントが、直近30日に1回以上使われた | 機械 | 会話の記録に、F8の名前での起動がある | 測定できず |
| F10 | コネクタ（外部サービスとのつなぎ）が1つ以上ある | 機械 | 設定に外部接続（MCPサーバー）の定義がある。または会話の記録に外部接続の道具の呼び出しがある | `config.toml` に `mcp_servers` の定義がある |
| F11 | コネクタが、直近30日に1回以上使われた | 機械 | 会話の記録に、外部接続の道具（名前が `mcp__` で始まる）の呼び出しがある | 測定できず |

### 安全（4項目）― 取り返しのつかないことを止められるか

| ID | 項目 | 判定 | Claude Code での見方 | Codex での見方 |
|---|---|---|---|---|
| S1 | よくある形のキーが、コードや設定に直接書かれていない | 機械 | 作業フォルダのGit管理下のテキストと、設定ファイルを、5-5 の決まりで走査する。0件なら○ | 同じ（設定は `config.toml`） |
| S2 | 秘密ファイルを読ませない設定がある | 機械 | 禁止の設定（`permissions.deny`）に、`.env` などの秘密ファイルの読み取りを止める行がある | 測定できず |
| S3 | 取り返しのつかない操作が、承認制か禁止になっている | 機械 | 禁止か承認の設定（`deny`／`ask`）に、削除・強制上書き・送信・公開のどれかを対象にした行がある | 承認の方式が「必要なときに確認」で、制限なしの実行モードではない |
| S4 | 既定のモードが「全部許す」になっていない | 機械 | 既定のモードが、確認をすべて省くモードではない | 「確認しない」と「制限なし」の組み合わせではない |

### 育つ・残る（3項目）― 使うほど資産が溜まるか

| ID | 項目 | 判定 | 見方（道具共通） |
|---|---|---|---|
| G1 | 指示書がGitで管理され、リモートにもある | 機械 | 作業フォルダがGitのリポジトリで、リモートがあり、指示書がGitの管理下にある |
| G2 | 個人用と共有用の指示が分かれている | 機械 | 全体用（個人）の指示書と、作業フォルダ用の指示書の両方に中身がある。または個人用の上書きファイルがある |
| G3 | 人が書かなくても、記録が残る仕組みがある | 機械＋AI | 会話の終わりや区切りで動くフック、または定時実行がある（機械）。あった場合、その名前と中身から「記録を残す仕組みか」をAIが判定する。AIの自動メモ機能は数えない |

### 任せ方（5項目）― 人の出番が判断に絞られているか

人が次の5つの係をやらずに済んでいるかを見る。

| ID | 人がやらずに済んでいる係 | 項目 | 判定 | Claude Code での見方 | Codex での見方 |
|---|---|---|---|---|---|
| D1 | 承認ボタンを押す係 | いつもの安全な操作は、確認なしで通る | 機械 | 許可の設定（`permissions.allow`）に行がある。または既定のモードが自動で判断するモード | 承認の方式が、毎回確認する方式ではない |
| D2 | 起動する係 | 繰り返す仕事が、人が起動しなくても始まり、直近30日に動いた | 機械＋本人の回答 | 定時実行の定義（OSの定時実行、道具の定期タスク）があり、その出力やログが直近30日に更新されている。定義はあるが動いた跡を読めないときは、本人に聞く | 同じ（自動化の定義） |
| D3 | 検査する係 | 終わる前の確認を、仕組みがやっている | 機械＋AI | 終了時に動くフックがある、または読むだけに絞った確認役のエージェントがある（機械）。どちらもなければ、指示書に「終える前に確かめる」決まりが書かれているかをAIが判定 | 終了時のフックがあるか（機械）。なければ指示書をAIが判定 |
| D4 | 伝言する係 | 役割の違うエージェントが、人を挟まずに続けて動いた記録が1件以上ある | 機械 | 1つの会話の中で、人の発言を挟まずに、自作のエージェントが2種類以上起動されている | 測定できず |
| D5 | 付きっきりで見る係 | 人の発言を挟まずに、20回以上続けて動いた会話が1件以上ある | 機械 | 人の発言を挟まない道具の呼び出しが、20回以上続いた会話がある | 測定できず |

## 5. 数え方の決まり

### 5-1. どの道具を「使っている」と見るか

その道具の設定フォルダがあり、設定ファイルか直近30日の会話の記録のどちらかがある。

### 5-2. 複数の道具を使っている場合

- **欠点がないことを見る項目**（安全の柱の4項目と、F2「長すぎない」、F4「矛盾がない」）: 測れた道具の**全部**が満たしていれば○。1つでも満たさなければ×。片方の道具の指示書に矛盾があるのに、もう片方に矛盾がないから○、とはしない。
- **あることを見る項目**（上以外）: 測れた道具の**どれか1つ**が満たしていれば○。
- どちらの決まりで合わせるかは、`items.json` に項目ごとに持つ。
- どの道具でも測れなければ「測定できず」。
- レポートの詳細ページには、道具ごとの結果も並べる。

### 5-3. 会話の記録の読み方（Claude Code）

- 場所は `~/.claude/projects/*/*.jsonl`。対象は、直近30日に1行以上の記録がある会話。
- **人の発言の数え方は、わざと厳しくする。** `type` が `user` の行で、道具の結果（`tool_result`）を含まないものは、システムの通知も含めてすべて「人の発言」として扱い、連続を切る。こうしておけば、数え方の違いで○が増えることがない。
- D5 で数えるのは、道具の呼び出し（`tool_use`）の数。1つの発言の中に複数の呼び出しがあれば、その数だけ数える。
- D5 の20回は仮の線。変えるときは仕様書を直す。

### 5-4. 作業フォルダ

点検を頼まれたときにAIがいるフォルダ。指示書・Git・キーの走査はここを見る。
設定・スキル・エージェント・会話の記録は、利用者の全体の設定フォルダも見る。

### 5-5. キーの走査（S1）

- 対象は、作業フォルダのGit管理下のテキストファイル（1ファイル1MBまで）と、道具の設定ファイル。Gitのリポジトリでなければ、設定ファイルだけを見る。
- **ファイルの一覧は `git ls-files -z` で取る。** 日本語など、英数字以外の名前のファイルも必ず走査する（v2 の実装は、こうした名前のファイルを黙って飛ばしていた）。
- `.env` など、Gitの対象外になっているファイルは走査しない（そこに置くのが正しいため）。リンクはたどらない。
- 探すものは2種類。
  - **キーの形**: 主要なサービスのキーの形（OpenAI・Anthropic の `sk-` 系、Google の `AIza` 系、GitHub、Slack、AWS、秘密鍵の見出し）。前後が英数字やハイフンで続いている場合（普通の単語や、画像データの途中）は数えない。
  - **設定ファイルの中の、名前でわかる秘密**（設定ファイルだけが対象）: 項目名に `token`・`secret`・`api_key`・`apikey`・`password`・`authorization` を含み、値が8文字以上の文字列で直接書かれているもの。値が環境変数の参照（`${…}`、`$NAME`、`env:` など）の場合は数えない。
- **見本は数えない。** 値に `xxxx`・`your`・`example`・`placeholder`・`replace`・`dummy`・`changeme`・`<…>`・`...` を含むもの、同じ文字が6回以上続くもの、英小文字とハイフンだけでできているものは、見本として除く。大文字と小文字は区別しない。**英小文字・数字・ハイフンだけでできていて、ハイフンが2つ以上あるもの**（`sk-` の後ろが `名前-用途-2026-07` のような、命名の決まりや名前の例）も除く。本物のキーは、大文字と小文字と数字が混ざった長い文字列だからである。
  - この「名前らしい文字列」の除外は、`sk-` 系の形にだけ使い、サービスを示す先頭の部分（`sk-`、`sk-ant-`、`sk-proj-` など）を除いた残りで判定する。Slack・GitHub・AWS・Google の形には使わない（先頭の部分だけで種類が決まり、小文字と数字とハイフンだけの本物のトークンがありうるため）。
- 走査しなかったファイルの数（1MBを超えた、読めなかった）を数えて、参考の数字に出す。
- 出力するのは**件数と種類だけ**。値・ファイル名・行番号は出さない。

### 5-6. AIの判断

- 質問の文面は `items.json` に固定で持つ。AIは「はい・いいえ」と、根拠の行番号を答える。
- AIは同じ質問を、最初の答えを見ずにもう一度判定する。**2回の答えが違ったら「測定できず」にする。**
- レポートには行番号だけを出し、本文は引用しない。
- AIが読むべきファイルの一覧は、スクリプトが `ai_targets.json` に出す（機械の判定と同じファイルをAIに読ませるため）。このファイルは出力フォルダの中だけに置く手元用で、レポートにも `result.json` にも入れない。

### 5-7. 外部プログラムの起動

- 起動してよいのは、Git（一覧と状態を読むサブコマンドだけ）と Chrome（PDFの書き出しだけ）。起動は、スクリプトの中の1か所の関数を必ず通す。引数は必ずリストで渡し、シェルを通さない。
- Git は、利用者や点検対象のリポジトリの設定に書かれたプログラムが動かないようにして呼ぶ（全体の設定とシステムの設定を読ませない。`core.fsmonitor` と `core.hooksPath` を無効にする）。
- **この2つの決まりは、起動の入口の関数そのものが強制する。** 入口の関数は、Git のサブコマンドを「読むだけのものの一覧」と照合し、一覧にないもの（`clone`・`fetch`・`pull`・`push`・`ls-remote` など通信するものを含む）は起動しない。安全な環境と設定の指定も、呼び出す側に任せず入口の関数が必ず付ける。
- 呼び出す側が Git に渡してよいのは、「サブコマンドとその引数」だけ。サブコマンドの前に置くオプション（`-C`、`--git-dir`、`--work-tree`、`--namespace`、`--exec-path`、`-c` など）が渡されたら、入口の関数は起動しない。作業するフォルダは、オプションではなく、起動時の作業フォルダの指定で渡す。
- Chrome は、出力フォルダの中に作った専用の設定フォルダ（`--user-data-dir`）で起動し、終わったらそのフォルダを消す。利用者のふだんの Chrome の設定には触れない。
- **起動する命令の形は、次の3つに固定する。入口の関数は、この3つ以外を受け付けない。**
  1. `git ls-files -z`（Gitの管理下にあるファイルの一覧を読む）
  2. `git remote`（引数なし。リモートがあるかを読む）
  3. Chrome で、出力フォルダの中のHTMLを、出力フォルダの中のPDFに書き出す命令
  - Git も Chrome も、**プログラムの場所は入口の関数が自分で決める**。呼び出す側からは渡させない。Chrome は、決まった場所の一覧と、決まった名前（完全に一致するものだけ）から探す。「chrome を含む名前」のような部分一致では選ばない。
  - 呼び出す側が渡せるのは、作業フォルダ（Git の2つ）と、HTML・PDF・専用の設定フォルダの場所（Chrome）だけ。Chrome に渡す3つの場所は、どれも出力フォルダの中でなければ起動しない。追加の引数は渡せない。
  - 使っていないサブコマンド（`config`、`rev-parse` など）は、許可の一覧に入れない。
- 通信の機能（`socket`、`urllib.request`、`http.client`、`requests` など）は読み込まない。シェルを通す実行、文字列をコードとして実行する機能、動的な読み込みも使わない。

## 6. 型の名前

柱の達成率から機械的に決める。80%以上を「強い」、60%未満を「薄い」とする。

| 条件 | 型の名前 |
|---|---|
| 4本とも強い | 全体が揃っている型 |
| 強い柱と薄い柱がある | 「（強い柱）は強く、（薄い柱）が薄い型」。複数あるときは読点「、」でつなぐ（例: 「土台、任せ方は強く、安全が薄い型」） |
| 強い柱だけがあり、薄い柱がない | 「（強い柱）が強い型」 |
| 薄い柱だけがあり、強い柱がない | 「（薄い柱）が薄い型」 |
| 4本とも薄い | これから整える型 |
| どれにも当たらない | 全体がほどほどの型 |

柱の呼び名は「土台」「安全」「育つ仕組み」「任せ方」。レポートのどこでも、この4つの呼び名だけを使う（「育つ・残る」とは書かない）。複数の柱を並べるときは読点「、」でつなぐ（例: 「土台、育つ仕組み、任せ方が強い型」）。

## 7. レポート

- A4縦のPDF。HTMLのひな形（`templates/report.html`）に結果（`result.json`）を流し込み、利用者のPCにある Chrome で書き出す。Chrome が見つからなければ、HTMLを残して開き方を案内する。
- ひな形は差し替えられる作りにする。ひな形が読むのは `result.json` だけ。
- ページ構成:
  1. 表紙: 点数、型の名前、「全23項目中○項目を判定」、柱ごとの「満たした数／判定できた数」、次に直す項目を最大3つ。あわせて、次の2行を必ず入れる。
     - 「ハーネス＝AIの周りに置く設定・指示・道具の一式」
     - 「見ているのはPCに残る設定と記録だけ。チャット画面での利用は数えていない」
  2. 柱ごとの結果: 項目ごとに ○・×・測定できず、判定の種類、ひとことの説明。項目はIDの番号順（F1、F2、…、F10、F11）に並べる。結果の文字は本文と同じ大きさにする。
  3. 参考の数字（採点しない生の数）。数え方を添える。
     - スキル: 自分で用意した本数、そのうち直近30日に使われた本数、使用回数を多い順に並べた数字（既定では名前を出さない）
     - エージェント: 同じ形
     - コネクタ: つながっている数、直近30日の呼び出しの合計（既定では名前を出さない）
     - 最長の連続回数、毎回読まれる指示の合計行数とファイル数
     - キーの走査: 見つかった件数と種類、走査したファイル数、読まなかったファイル数。読まなかったファイルには「画像など文字でないもの、1MBを超えるもの」と理由を添える
     - 名前を出さないときの使用回数の数字の並びには、「多い順。少数の道具に偏っていないかの目安」と一言添える
     - `--show-names` を指定したときだけ、名前つきの表にする。その場合も、意味のない識別子（長い英数字の羅列）だけの名前は表に出さず、「ほか○件」にまとめる。名前つきのレポートには、各ページの下に「固有名を含みます」と出す。
     - 表がページをまたぐときは、次のページにも表の見出しを出す。
  4. この点検が見ていないもの: チャット画面での利用、道具ごとの測れない項目、キーの走査の限界（よくある形と、設定ファイルの中の名前でわかるものだけを探していること。1MBを超えるファイルと、Gitの対象外のファイルは見ていないこと。小文字だけの値や、小文字・数字・ハイフンだけの値は、名前や見本とみなして数えないこと）
- 表紙の説明の2行は、色のついた帯と重ならない位置に置く。
- 「次に直す項目」は、×の項目を、安全 → 土台 → 任せ方 → 育つ仕組み の順に並べて上から3つ。**項目名そのままではなく、何をすれば直るかを動詞で書く**（例: 「秘密ファイルを読ませない設定を足す」）。この文言は `items.json` に項目ごとに持つ。
- 配色は赤（#D8324A）と薄ピンク（#F8D4DD）。絵文字は使わない。

## 9. AIへの手順（AGENTS.md に書く内容）

1. `collect.py` などのスクリプトを先に読み、読むだけ・通信なしであることを確かめてから実行する。
2. `collect.py` を実行する。
3. `facts.json` にある「AIへの質問」に、5-6 の決まりで答え、`ai_judgments.json` に書く。本人への質問があれば、本人に聞いて答えを書く。
4. `score.py` と `render.py` を実行する。
5. 点数、型、次に直す3つを、短く本人に伝える。レポートの場所を伝える。**人に渡してよいのは `report.pdf` と `report.html` だけ**で、ほかのファイルは手元用だと伝える。`ai_targets.json` は、レポートができたら消す。
6. 利用者の設定は書き換えない。直すのは、本人に頼まれてから。
