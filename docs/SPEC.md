# ハーネス点検 仕様書（v2.4）

2026-11-11 確定。採点の中身を変えるときは、先にこのファイルを直す。
v2.1 は、1周目のレビューで見つかった仕様の不備を直したもの。変更点は12章にまとめてある。
v2.2 は、`result.json` に項目ごとの理由（`reason`・`facts`、schema_version 3）を足したもの。変更点は13章。採点の中身は変えていない。
v2.3 は、Codex の新しい設定の書き方（許可の仕組み）と、会話の記録のうち読める分の読み取りを足したもの。変更点は14章。
v2.4（2026-11-18）は、今月の使用量（時間・トークン）とスキル・エージェントの本数を表紙近くに出すこと、使われた形跡の項目（F6・F9・F11）を回数の段階で評価することを足したもの（`result.json` schema_version 4）。変更点は15章。

## 1. これは何か

AIエージェント（Claude Code、Codex など）を使っている人が、自分の「ハーネス」を自分で点検する道具。
ハーネスとは、AIの周りに置く設定・指示・道具の一式のこと。

使い方は1つ。利用者が自分のAIに「このリポジトリを読んで、手順どおりに私の環境を点検して」と頼む。
AIが手順書に従って事実を集め、点数つきのレポート（PDF）を出す。

- 主な利用者は、自分で走らせる個人。研修で使う場合も、同じ道具を各自が走らせる。
- 特定の会社やチームの事情は、この道具に持ち込まない。

## 2. 設計の原則

1. **道具に依らない点検項目と、道具ごとの読み取り部品を分ける。** 項目は `items.json` の1か所で定義する。道具ごとの事実の集め方は `readers/` に置く。最初の部品は Claude Code と Codex。
2. **測れないものは×にしない。** 「測定できず」として、点数の分母から外す。
3. **割合は採点しない。** 採点に使うのは、「ある／ない」と「直近30日に1回以上の記録がある／ない」の二値だけ。回数や行数は参考欄に生の数で載せる。
4. **1つの設定は1つの項目でしか数えない。**
5. **判定の出どころを必ず示す。** 項目ごとに「機械」「AIの判断」「本人の回答」のどれで決めたかをレポートに出す。
6. **「人が入らないほど良い」とはしない。** 任せ方の柱と安全の柱を別に立て、両方を見る。
7. **読むだけ。** 利用者のPCに書き込むのは、出力フォルダの中だけ。通信はしない。
8. **秘密と固有名を出さない。** キーの値は絶対に出力しない。フォルダ名・ファイルの本文・会話の本文は、レポートに出さない。**スキル・エージェント・コネクタの名前も、既定では出さない**（取引先名などが入っていることがあるため）。名前は、本人が `--show-names` を指定したときだけ出す。
9. **起動してよい外部プログラムは、Git と Chrome だけ。** それ以外は起動しない（5-7）。

## 3. 点数

- 柱は4本。柱ごとに「満たした数 ÷ 判定できた数」を出す。
- **点数は、4本の柱の達成率の平均を100点満点にして四捨五入したもの。** 判定できた項目が0の柱は、平均から外す。
- 点数の横に「23項目中○項目を判定」を必ず添える。
- 合計点のほかに「型」の名前を出す（6章）。レベルや順位は出さない。
- **柱の達成率は、○＝1／×＝0の単純な数え方ではなく、部分点（0・1／3・2／3・満点の4段階）を足して計算する項目がある**（F6・F9・F11。使われた形跡を回数で見る項目。15章・5-10）。「満たした数」（○の数）自体の数え方は変えていない。

## 4. 点検項目（23項目）

判定の種類: **機械**＝スクリプトが決める ／ **AI**＝AIが決まった質問に「はい・いいえ」で答える ／ **機械＋AI**＝機械で○にならなかったときだけAIが判定する。

「使用の記録」は、直近30日の会話の記録から数える。

### 土台（11項目）― 道具が揃い、使われているか

### 安全（4項目）― 取り返しのつかないことを止められるか

| ID | 項目 | 判定 | Claude Code での見方 | Codex での見方 |
|---|---|---|---|---|
| S1 | よくある形のキーが、コードや設定に直接書かれていない | 機械 | 作業フォルダのGit管理下のテキストと、設定ファイルを、5-5 の決まりで走査する。0件なら○ | 同じ（設定は `config.toml`） |
| S2 | 秘密ファイルを読ませない設定がある | 機械 | 禁止の設定（`permissions.deny`）に、`.env` などの秘密ファイルの読み取りを止める行がある | 自分で決めた許可の仕組み（14-1）の中に、`.env` などの読み取りを拒否する行があるかで判定する。組み込みの仕組み（自分でパスを指定できないもの）のときは測定できず |
| S3 | 取り返しのつかない操作が、承認制か禁止になっている | 機械 | 禁止か承認の設定（`deny`／`ask`）に、削除・強制上書き・送信・公開のどれかを対象にした行がある | 承認の方式が「必要なときに確認」で、制限なしの実行モードではない |
| S4 | 既定のモードが「全部許す」になっていない | 機械 | 既定のモードが、確認をすべて省くモードではない | 「確認しない」と「制限なし」の組み合わせではない |

### 育つ・残る（3項目）― 使うほど資産が溜まるか

| ID | 項目 | 判定 | 見方（道具共通） |
|---|---|---|---|
| G1 | 指示書がGitで管理され、リモートにもある | 機械 | 作業フォルダがGitのリポジトリで、リモートがあり、指示書がGitの管理下にある |
| G2 | 個人用と共有用の指示が分かれている | 機械 | 全体用（個人）の指示書と、作業フォルダ用の指示書の両方に中身がある。または個人用の上書きファイルがある |

### 任せ方（5項目）― 人の出番が判断に絞られているか

人が次の5つの係をやらずに済んでいるかを見る。

| ID | 人がやらずに済んでいる係 | 項目 | 判定 | Claude Code での見方 | Codex での見方 |
|---|---|---|---|---|---|
| D1 | 承認ボタンを押す係 | いつもの安全な操作は、確認なしで通る | 機械 | 許可の設定（`permissions.allow`）に行がある。または既定のモードが自動で判断するモード | 承認の方式が、毎回確認する方式ではない |
| D2 | 起動する係 | 繰り返す仕事が、人が起動しなくても始まり、直近30日に動いた | 機械＋本人の回答 | 定時実行の定義（OSの定時実行、道具の定期タスク）があり、その出力やログが直近30日に更新されている。定義はあるが動いた跡を読めないときは、本人に聞く | 同じ（自動化の定義） |
| D3 | 検査する係 | 終わる前の確認を、仕組みがやっている | 機械＋AI | 終了時に動くフックがある、または読むだけに絞った確認役のエージェントがある（機械）。どちらもなければ、指示書に「終える前に確かめる」決まりが書かれているかをAIが判定 | 終了時のフックがあるか（機械）。なければ指示書をAIが判定 |
| D4 | 伝言する係 | 役割の違うエージェントが、人を挟まずに続けて動いた記録が1件以上ある | 機械 | 1つの会話の中で、人の発言を挟まずに、自作のエージェントが2種類以上起動されている | 測定できず |
| D5 | 付きっきりで見る係 | 人の発言を挟まずに、20回以上続けて動いた会話が1件以上ある | 機械 | 人の発言を挟まない道具の呼び出しが、20回以上続いた会話がある | 会話の記録のうち、圧縮されておらず読める分だけを見て判定する（14-2）。読める記録が無ければ測定できず |

## 5. 数え方の決まり

### 5-1. どの道具を「使っている」と見るか

その道具の設定フォルダがあり、設定ファイルか直近30日の会話の記録のどちらかがある。

### 5-2. 複数の道具を使っている場合

- **欠点がないことを見る項目**（安全の柱の4項目と、F2「長すぎない」、F4「矛盾がない」）: 測れた道具の**全部**が満たしていれば○。1つでも満たさなければ×。片方の道具の指示書に矛盾があるのに、もう片方に矛盾がないから○、とはしない。
- **あることを見る項目**（上以外）: 測れた道具の**どれか1つ**が満たしていれば○。
- どちらの決まりで合わせるかは、`items.json` に項目ごとに持つ。
- どの道具でも測れなければ「測定できず」。
- レポートの詳細ページには、道具ごとの結果も並べる。

### 5-3. 会話の記録の読み方（Claude Code）

- 場所は `~/.claude/projects/*/*.jsonl`。対象は、直近30日に1行以上の記録がある会話。
- **人の発言の数え方は、わざと厳しくする。** `type` が `user` の行で、道具の結果（`tool_result`）を含まないものは、システムの通知も含めてすべて「人の発言」として扱い、連続を切る。こうしておけば、数え方の違いで○が増えることがない。
- D5 で数えるのは、道具の呼び出し（`tool_use`）の数。1つの発言の中に複数の呼び出しがあれば、その数だけ数える。
- D5 の20回は仮の線。変えるときは仕様書を直す。

### 5-4. 作業フォルダ

点検を頼まれたときにAIがいるフォルダ。指示書・Git・キーの走査はここを見る。
設定・スキル・エージェント・会話の記録は、利用者の全体の設定フォルダも見る。

### 5-5. キーの走査（S1）

- 対象は、作業フォルダのGit管理下のテキストファイル（1ファイル1MBまで）と、道具の設定ファイル。Gitのリポジトリでなければ、設定ファイルだけを見る。
- **ファイルの一覧は `git ls-files -z` で取る。** 日本語など、英数字以外の名前のファイルも必ず走査する（v2 の実装は、こうした名前のファイルを黙って飛ばしていた）。
- `.env` など、Gitの対象外になっているファイルは走査しない（そこに置くのが正しいため）。リンクはたどらない。
- 探すものは2種類。
  - **キーの形**: 主要なサービスのキーの形（OpenAI・Anthropic の `sk-` 系、Google の `AIza` 系、GitHub、Slack、AWS、秘密鍵の見出し）。前後が英数字やハイフンで続いている場合（普通の単語や、画像データの途中）は数えない。
  - **設定ファイルの中の、名前でわかる秘密**（設定ファイルだけが対象）: 項目名に `token`・`secret`・`api_key`・`apikey`・`password`・`authorization` を含み、値が8文字以上の文字列で直接書かれているもの。値が環境変数の参照（`${…}`、`$NAME`、`env:` など）の場合は数えない。
- **見本は数えない。** 値に `xxxx`・`your`・`example`・`placeholder`・`replace`・`dummy`・`changeme`・`<…>`・`...` を含むもの、同じ文字が6回以上続くもの、英小文字とハイフンだけでできているものは、見本として除く。大文字と小文字は区別しない。**英小文字・数字・ハイフンだけでできていて、ハイフンが2つ以上あるもの**（`sk-` の後ろが `名前-用途-2026-07` のような、命名の決まりや名前の例）も除く。本物のキーは、大文字と小文字と数字が混ざった長い文字列だからである。
  - この「名前らしい文字列」の除外は、`sk-` 系の形にだけ使い、サービスを示す先頭の部分（`sk-`、`sk-ant-`、`sk-proj-` など）を除いた残りで判定する。Slack・GitHub・AWS・Google の形には使わない（先頭の部分だけで種類が決まり、小文字と数字とハイフンだけの本物のトークンがありうるため）。
- 走査しなかったファイルの数（1MBを超えた、読めなかった）を数えて、参考の数字に出す。
- 出力するのは**件数と種類だけ**。値・ファイル名・行番号は出さない。

### 5-6. AIの判断

- 質問の文面は `items.json` に固定で持つ。AIは「はい・いいえ」と、根拠の行番号を答える。
- AIは同じ質問を、最初の答えを見ずにもう一度判定する。**2回の答えが違ったら「測定できず」にする。**
- レポートには行番号だけを出し、本文は引用しない。
- **AIは理由の文を書かない。** 項目ごとの理由（5-8）は、AIの答え（はい・いいえ・食い違い・未回答）と根拠の行の数から、決まった文の型で作る。`ai_judgments.json` に文が書かれていても使わない。AIが読むのは利用者の指示書やスキルの中身で、社名・人名などの固有名は日本語の文に紛れると機械では見分けられないため。
- AIが読むべきファイルの一覧は、スクリプトが `ai_targets.json` に出す（機械の判定と同じファイルをAIに読ませるため）。このファイルは出力フォルダの中だけに置く手元用で、レポートにも `result.json` にも入れない。

### 5-7. 外部プログラムの起動

- 起動してよいのは、Git（一覧と状態を読むサブコマンドだけ）と Chrome（PDFの書き出しだけ）。起動は、スクリプトの中の1か所の関数を必ず通す。引数は必ずリストで渡し、シェルを通さない。
- Git は、利用者や点検対象のリポジトリの設定に書かれたプログラムが動かないようにして呼ぶ（全体の設定とシステムの設定を読ませない。`core.fsmonitor` と `core.hooksPath` を無効にする）。
- **この2つの決まりは、起動の入口の関数そのものが強制する。** 入口の関数は、Git のサブコマンドを「読むだけのものの一覧」と照合し、一覧にないもの（`clone`・`fetch`・`pull`・`push`・`ls-remote` など通信するものを含む）は起動しない。安全な環境と設定の指定も、呼び出す側に任せず入口の関数が必ず付ける。
- 呼び出す側が Git に渡してよいのは、「サブコマンドとその引数」だけ。サブコマンドの前に置くオプション（`-C`、`--git-dir`、`--work-tree`、`--namespace`、`--exec-path`、`-c` など）が渡されたら、入口の関数は起動しない。作業するフォルダは、オプションではなく、起動時の作業フォルダの指定で渡す。
- Chrome は、出力フォルダの中に作った専用の設定フォルダ（`--user-data-dir`）で起動し、終わったらそのフォルダを消す。利用者のふだんの Chrome の設定には触れない。
- **起動する命令の形は、次の3つに固定する。入口の関数は、この3つ以外を受け付けない。**
  1. `git ls-files -z`（Gitの管理下にあるファイルの一覧を読む）
  2. `git remote`（引数なし。リモートがあるかを読む）
  3. Chrome で、出力フォルダの中のHTMLを、出力フォルダの中のPDFに書き出す命令
  - Git も Chrome も、**プログラムの場所は入口の関数が自分で決める**。呼び出す側からは渡させない。Chrome は、決まった場所の一覧と、決まった名前（完全に一致するものだけ）から探す。「chrome を含む名前」のような部分一致では選ばない。
  - 呼び出す側が渡せるのは、作業フォルダ（Git の2つ）と、HTML・PDF・専用の設定フォルダの場所（Chrome）だけ。Chrome に渡す3つの場所は、どれも出力フォルダの中でなければ起動しない。追加の引数は渡せない。
  - 使っていないサブコマンド（`config`、`rev-parse` など）は、許可の一覧に入れない。
- 通信の機能（`socket`、`urllib.request`、`http.client`、`requests` など）は読み込まない。シェルを通す実行、文字列をコードとして実行する機能、動的な読み込みも使わない。

### 5-8. 項目ごとの理由（result.json の reason・facts）

- 23項目すべてに、なぜ「満たしている」「満たしていない」「判定できず」になったかを、`reason`（日本語の1〜2文・300字まで）と `facts`（数・状態と基準の値。6個まで）で付ける。形の正本は `docs/RESULT_SCHEMA.md`。
- 書くのは「今の状態」（何件・何行・何回・有る無し）と「基準とどう比べたか」だけ。意味づけや評価の言葉は書かない。判定できなかった項目は、何が足りなかったかを書く。
- 文は、項目ごと・状態ごとに決まった型（`reasons.py`）に、整数と決まった語だけを差し込んで作る。名前・パス・設定の項目名・本文・AIの文は差し込まない。`--show-names` でも同じ。
- `score.py` は出来上がった文を検査し（パス・拡張子つきの名前・英小文字の識別子・URL・メール・決まった5語以外の英字など）、当たったら定型文に置き換える。
- 理由を組み立てるための数（いちばん長い指示ファイルの行数、許可の設定の行数など）は `collect.py` が `facts.json` に入れる。数だけで、名前は入れない。

### 5-9. 説明の一覧（result.json の inventory）

- スキル・エージェント・コネクタごとに、何をするものかを**固有名詞を使わずに1文**（80字まで）で書いた一覧を `result.json` に入れる。スキルには分類（集計・資料・メール・相談・調べもの・自動化・その他）を付ける。名前は入れない。形の正本は `docs/RESULT_SCHEMA.md`。
- 説明は機械では作れないので、AIの判断の段（手順3）で、AIが `ai_targets.json` の `INVENTORY` に書かれたファイルを読んで1文ずつ書く。入れてはいけないもの（名前・場所・社名・人名・商品名・案件名・取引先名・地名・社内の呼び名・URL・メール・キー）と言い換えの例は `AGENTS.md` に書く。コネクタは一般の製品の種類（チャットの道具・メール・表計算・予定表）で書き、製品名も入れない。
- `score.py` は、手元の名前の一覧と突き合わせ、名前・場所・識別子らしい語などが1つでも当たった説明を捨てて「（説明を作れませんでした）」に置き換える（`inventory.py`）。置き換えた数を参考の数に残す。名前の一覧（`ai_targets.json`）が無ければ、確かめられないので全部置き換える。
- 社名・人名は、誤って止めることが少ない印（株式会社・御中、固有の語＋工務店・建設など、名前＋さん・様・部長など）だけを機械で見る（`propernoun.py`）。場所の印（〇〇展示場・〇〇支店）とカタカナの連続は、一般の言い方と見分けられないので見ない。
- 機械で見つけきれない日本語の社名・人名は、送るスキルの下見で説明の一覧を本人に全部見せ、目を通してもらうことで補う。
- `facts.json` には、一覧の下ごしらえ（手元だけの番号と回数）だけを入れ、名前は `ai_targets.json`（手元用・レポートができたら消す）にだけ置く。

### 5-10. 今月の使用量と、使われた形跡の段階評価（v2.4）

**今月の使用量（時間・トークン・本数）**

- 「今月」＝実行した日の**日本時間の暦月**（1日0時〜今）。UTCの記録の時刻を日本時間に直してから、月の境目（1日0時）と比べる。
- **時間の数え方**: 会話の記録の時刻（種類を問わず全行）を集め、隣り合う時刻の間隔が**5分（300秒）以内**の連続を「使っていた時間」として足す。5分を超えた空きは数えない。5分ちょうどは含む（300秒以内）。Claude Code と Codex は別々に数え、合計は2つを単純に足したもの（同時に両方を使っていた時間は重複して数える。レポートの「見ていないもの」に明記する）。
- **トークンの数え方**:
  - Claude Code: 会話の記録の `usage`（`input_tokens`・`output_tokens`・`cache_creation_input_tokens`・`cache_read_input_tokens`）を、今月の分だけ足す。表示名は「入力」「出力」「キャッシュ（読み書きの合計）」。
  - Codex: 会話の記録のうち、読める（圧縮されていない）`token_usage_record` の `payload.usage` を今月の分だけ足す。`input_tokens`→入力、`output_tokens`＋`reasoning_output_tokens`→出力、`cached_input_tokens`→キャッシュの読み、`cache_write_input_tokens`→キャッシュの書き。
  - 圧縮（`.jsonl.zst`）で読めない記録が今月の分にあれば、件数をレポートに明記し、トークン・時間には含めない（推測で埋めない）。
- **本数**: 自分で用意したスキルの本数・自分で定義したエージェントの本数を、Claude Code と Codex に分けて出す（既存の F5・F8 と同じ数え方。15章）。名前は既定では出さない（原則8）。
- `result.json` には `usage_this_month`（時間・トークン）と `tool_counts`（本数）を新設し、レポートの表紙（点数のすぐ下）に出す（7章）。

**使われた形跡の段階評価（F6・F9・F11）**

- F6（スキル）・F9（エージェント）・F11（コネクタ）は、「直近30日に1回以上使われたか」という○・×の判定自体は変えない（5-2・既存の merge 規則もそのまま）。
- **柱の達成率（3章）に使う部分点だけを、回数に応じた4段階にする**：直近30日の使用回数（複数の道具が測れたときは合算）が、0回＝0、1〜4回＝3分の1、5〜19回＝3分の2、20回以上＝満点（3分の3）。境目の値は `items.json` の `usage_tier_boundaries` に置く（境目を変えるときはここを直す）。
- `result.json` の `items.<ID>.usage_tier`（F6・F9・F11のみ、他はnull）に `count`・`credit`・`label` を持ち、レポートの項目の行に「◯回（段階 2/3）」のように添える（7章）。`reason`・`facts` の文自体は変えない（5-8 の禁止のもの検査の対象外にするため。斜線はこの `usage_tier` フィールドにだけ使う）。
- なぜこの3項目だけか: `items.json` で「直近30日に1回以上使われた」（使用の記録そのものを数える）項目はこの3つだけ。D2（定時実行が動いたか）は使用回数ではなく「動いたか」の一度きりの確認のため対象外。

## 6. 型の名前

柱の達成率から機械的に決める。80%以上を「強い」、60%未満を「薄い」とする。

| 条件 | 型の名前 |
|---|---|
| 4本とも強い | 全体が揃っている型 |
| 強い柱と薄い柱がある | 「（強い柱）は強く、（薄い柱）が薄い型」。複数あるときは読点「、」でつなぐ（例: 「土台、任せ方は強く、安全が薄い型」） |
| 強い柱だけがあり、薄い柱がない | 「（強い柱）が強い型」 |
| 薄い柱だけがあり、強い柱がない | 「（薄い柱）が薄い型」 |
| 4本とも薄い | これから整える型 |
| どれにも当たらない | 全体がほどほどの型 |

柱の呼び名は「土台」「安全」「育つ仕組み」「任せ方」。レポートのどこでも、この4つの呼び名だけを使う（「育つ・残る」とは書かない）。複数の柱を並べるときは読点「、」でつなぐ（例: 「土台、育つ仕組み、任せ方が強い型」）。

## 9. AIへの手順（AGENTS.md に書く内容）

1. `collect.py` などのスクリプトを先に読み、読むだけ・通信なしであることを確かめてから実行する。
2. `collect.py` を実行する。
3. `facts.json` にある「AIへの質問」に、5-6 の決まりで答え、`ai_judgments.json` に書く。本人への質問があれば、本人に聞いて答えを書く。
4. `score.py` と `render.py` を実行する。
5. 点数、型、次に直す3つを、短く本人に伝える。レポートの場所を伝える。`report.pdf` と `report.html` は本人が人に見せてよい。`result.json` はそのまま人に渡すものではなく、SHO-SAN に送る場合は、送るスキル（sho-san-share）が同意を取ったうえで `result.json` だけを送る。`facts.json`・`ai_judgments.json`・`ai_targets.json` は手元用で、送られない。`ai_targets.json` は、レポートができたら消す。
6. 利用者の設定は書き換えない。直すのは、本人に頼まれてから。

Codex を使っている人の点検結果の多くが「測定できず」になる問題を直したもの。採点の仕組み（4章の各項目の意味・3章の点数の出し方）は変えていない。Codex の読み取り部品（`readers/codex.py`）が、新しい設定の書き方と、会話の記録のうち読める分を見るようになった。

### 14-1. 許可の仕組み（`default_permissions` 等）を読む

Codex の設定は、承認の方式（`approval_policy`）と実行の制限（`sandbox_mode`）を別々に書く古い書き方と、「許可の仕組み」（`default_permissions`）に一つにまとめて書く新しい書き方の両方がある（公式の設定の説明で確認済み）。古い書き方しか読んでいなかったため、新しい書き方だけの設定では、安全の柱の S3・S4 と任せ方の柱の D1 が「測定できず」になっていた。

- `default_permissions` の値が、組み込みの名前（`:read-only`・`:workspace`・`:danger-full-access`）なら、`sandbox_mode` と同じ意味として扱う（制限なしの実行モードかどうかの判定に使う）。組み込みの名前の比較は大文字小文字を区別しない。
- `default_permissions` の値が、自分で決めた名前（組み込み以外）なら、同じ名前の `[permissions.<名前>]` の中の許可の仕組み（`filesystem`）を見る。名前は大文字小文字をそのまま使う（自分で決めた名前はテーブル名として大文字小文字が意味を持つため、組み込みの名前の判定とは別に扱う）。
  - この中に、`.env` など秘密ファイルらしいパスを「拒否」（`deny`）にしている設定があれば、S2（秘密ファイルを読ませない設定）を○と判定する。無ければ×。公式の書き方（`":workspace_roots"` という入れ子・一行テーブルの中に書く形）・別表記（入れ子テーブルの見出しで書く形）のどちらも数える。この設定自体が無い・組み込みの名前のときは、自分でパスを指定できないため、S2 は引き続き「測定できず」。
- **古い書き方（`sandbox_mode`）があるときは、`default_permissions` は判定に使わない。** 公式の案内が「同時に使わない」としているため、両方書かれていたら古い方を優先する（新しい方を見て判定を変えない）。
- 承認の方式（「必要なときに確認」かどうか）の判定は、`approval_policy` を読む（変更なし）。`default_permissions` だけでは承認の方式はわからないため、推測で埋めない。**`approval_policy` が無いときの Codex 自体の既定の承認方針は、公式の設定の説明でも明記されていない（「既定値: 書かれていない」）。** 本ツールは、`approval_policy` が無ければ「確認しない」でも「毎回確認」でもない、という本ツールの既定の扱い（原則2「測定できないものは×にしない」）で判定しており、Codex 自体が実際にどう振る舞うかを確認した結果ではない。
- **TOML の読み方**: 標準の `tomllib`（Python 3.11 以上）があれば、それで正しく読む（入れ子・一行テーブルも含めて、公式の書き方をそのまま読める）。壊れた TOML（構文エラー）なら、S2・S3・S4・D1 をすべて「測定できず」にする（読めなかったものを○・×どちらにも寄せない）。`tomllib` が無い環境（3.9・3.10）は簡易読み取りにフォールバックする。簡易読み取りは、**クォートされた文字列の値だけを認める**（クォート無しの値は、無効な TOML として記録しない）。

### 14-2. 会話の記録のうち、読める分だけを使う

Codex の会話の記録（`~/.codex/sessions/`）は、最近のものは平文の `.jsonl`、時間が経つと `.jsonl.zst`（zstd 圧縮）になる。圧縮形式は Python 標準機能だけでは読めない（3.14 未満に `compression.zstd` が無い）ため、**平文のまま残っている分だけ**を読み、F11（コネクタの使用）・D5（人の発言を挟まない連続呼び出し）を判定する。

- ファイル名（`rollout-2026-11-16T16-17-47-<id>.jsonl` の形）から日時を読み、直近30日の分だけを対象にする。圧縮済みでもファイル名の日時は読めるので、圧縮分の件数も数える（読めなかった件数として `facts.json` に残し、理由の文にも反映する。推測で埋めない）。
- D5: 会話の記録の中の `response_item` のうち、`role` が `user` の `message` を「人の発言」の区切りとし、道具の呼び出しらしい種類（`function_call`・`custom_tool_call`・`mcp_tool_call`・`local_shell_call`）が、人の発言を挟まずに何回続いたかを数える。名前には依らない機械的な数え方なので、どの道具が呼ばれたかを推測しない。**「人の発言」の区切りは `role` が `user` のときだけ**（`developer` など他の役割の行は区切りとして数えない）。
- F11: 道具の呼び出しのうち、`namespace` という項目が `mcp__` で始まるもの、**または種類そのものが `mcp_tool_call` のもの**（どちらか）を、外部接続の道具（コネクタ）の呼び出しとして数える（`namespace` の決まりは Claude Code 側の `mcp__` という名前の決まりと同じ。`mcp_tool_call` という種類は、どの道具が呼ばれたかの名前に依らず、D5 の道具呼び出しの数え方と揃えたもの）。どちらの印も無い記録では何も数えない（コネクタが無かったと決めつけない。安全側に倒す）。
- F6（自作スキルの使用）・F9（自作エージェントの使用）・D4（役割の違うエージェントが続けて動いた記録）は、読めた記録の中にも、これらを区別できる確実な仕組みが見つからなかったため、引き続き「測定できず」とする。理由の文は「会話の記録が読めない」ではなく「この項目を会話の記録から確かめる方法が無い」に変える（読めているのに読めないと書くのは不正確なため）。
- 読める記録が1件もないとき: 直近30日に記録が1件も無ければ「会話の記録が見つからなかったため、判定できませんでした」。記録はあるが全部圧縮されていて読めないときは「会話の記録が標準の機能で読めない形のため、判定できませんでした」。2つの理由を混同しない。

| 変更 | 理由 |

## 15. v2.3 からの変更点（v2.4）

2026-11-19 の研修で使うため、オーナー指示の3点を足したもの。採点の**仕組み**（4本の柱・判定の種類・○×測定できずの3値）は変えていない。変えたのは、柱の達成率の計算に使う部分点の作り方（3章・5-10）と、表紙・項目ページに出す情報（7章）。

| オーナーの指示 | 対応 |
|---|---|
| ①今月の使用時間・トークンを表紙の点数のすぐ下に出す | `usage_this_month`（`result.json` v4）。時間は記録の時刻の間隔が5分以内の連続を足す数え方（5-10）。トークンは Claude Code の `usage`、Codex の読める `token_usage_record` を今月の分だけ足す。Codex の圧縮で読めない分は件数を明記し含めない |
| ②スキルの本数・エージェントの数を出す | `tool_counts`（`result.json` v4）。Claude Code・Codex 別、既存の F5・F8 と同じ数え方。名前は既定では出さない（原則8のまま） |
| ③使われた形跡（F6・F9・F11）を回数で段階づける | `items.json` の `usage_tier_boundaries`（0回＝0、1〜4回＝3分の1、5〜19回＝3分の2、20回以上＝満点）。`items.<ID>.usage_tier` に `count`・`credit`・`label`。柱の達成率（3章）はこの部分点を足して計算する。○・×の判定自体（直近30日に1回以上使われたか）は変えていない |

### 15-1. 決め方（根拠）

- 「今月」＝実行した日の**日本時間**の暦月。UTCの記録をJSTに直して比べる（オーナー・海外時間のツールをまたぐため、タイムゾーンの取り違えが起きやすい箇所）。
- 時間の数え方の「5分」は、D5（人の発言を挟まない連続呼び出し20回）のような他の固定の仮の線と同じ位置づけの仮の値。変えるときはこのファイルを直す。
- 段階の対象をF6・F9・F11の3項目に絞った理由: `items.json` 全23項目のうち、「直近30日に1回以上使われた（＝使用の記録そのものを数える）」項目はこの3つだけ（D2は定時実行が動いたかどうかの一度きりの確認で、回数を数える項目ではないため対象外）。
- 柱の達成率は「○の数÷判定できた数」から「部分点の合計÷判定できた数」に変える。段階評価の無い項目は○＝1／×＝0のままなので、F6・F9・F11を含まない柱（安全・育つ仕組み・任せ方）は、この変更の前後で計算結果が変わらない（後方互換）。
- `status`（○・×・測定できず）自体は変えていない。「1回使えば合格」という○の表示はそのまま残し、合格の"重み"（達成率に効く部分点）だけを厳しくした。合格の基準自体を上げる（例: 20回未満は×にする）ことも検討したが、オーナー指示の原文が「柱の達成率は部分点を足して計算」であり、既存の「点数＝柱ごとの達成率の平均」の式を保つ指定と一致するため、この設計にした。
- 複数の道具が測れる項目（F11）は、段階を決める回数を道具間で**合計**する（5-2の「どれかが満たせば○」という既存の合わせ方とは別に、段階は回数の総量で見るほうが「どれだけ使っているか」の実態に近いと判断した）。

### 15-2. `result.json` の後方互換

- `schema_version` を3から4に上げた。**既存のキーは1つも削除・改名していない**（追加のみ）。
  - 新設: 最上位の `usage_this_month`・`tool_counts`、`items.<ID>.usage_tier`（F6・F9・F11以外はnull）。
  - `facts.json`（`collect.py` の出力）も同様にschema_versionを3から4に上げ、`score.py` はv4の`facts.json`だけを受け付ける（v2→v3のときと同じ運用。11章）。
- v3までの形しか知らない読み手（送るスキル sho-san-share・事例ボックス）は、新しいキーを単に無視すれば動き続ける（docs/RESULT_SCHEMA.md参照）。
